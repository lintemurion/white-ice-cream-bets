# GitHub Actions Build and Deploy: Design

Date: 2026-11-22
Owner: Kyle
Builds on: `2026-11-22-white-ice-cream-bets-design.md`

## Intent

Kyle wants deploys of White Ice Cream Bets to be repeatable and run by GitHub, not typed by hand on his machine. Every deploy should be the same steps, tested first, with no long-lived credentials.

## Goals

- **Deploy triggers (Kyle's decision):** every push to `main` (so every merged PR), and manual "Run workflow" (`workflow_dispatch`) from any branch Kyle picks.
- **Tests gate deploys:** every deploy runs the full suite (unit/UI tests plus the Firestore emulator tests) and the build first; any failure stops the deploy.
- **Tests on pull requests (Claude's call):** the same tests and build run on every PR, with no deploy, so a broken change is caught before merge.
- **Deploy what `firebase deploy` deploys today:** Hosting (the built site), Firestore rules generated by `npm run rules` with the admin email, and Firestore indexes.
- **Keyless auth (Kyle's decision):** GitHub Actions authenticates to Google Cloud via Workload Identity Federation (OIDC). No service account key is ever created or stored.

## Non-goals

- PR preview sites (Hosting preview channels).
- Required-reviewer approval gates on deploys (GitHub Environments protection rules need a paid plan for private repos).
- Deploying anything other than this one Firebase project.
- Changing the app itself.

## Anti-goals

- A long-lived credential that could deploy to the project or change the database if leaked.
- Any workflow run from outside this repository being able to deploy (the trust is pinned to `lintemurion/white-ice-cream-bets`).
- A deploy built with emulator or test settings (for example `demo-wicb` or the test admin email).
- Printing secrets or tokens in logs.

## Constraints

- Repo: private, `lintemurion/white-ice-cream-bets` on GitHub. Firebase project `whiteicecreambets`, free Spark plan, no card.
- CI needs Node 24 and Java 21 (firebase-tools 15 emulators need Java 21).
- `gcloud` is not installed on Kyle's machine. One-time Google Cloud setup runs in **Google Cloud Shell** (browser, already authenticated). Kyle runs those commands himself.
- Kyle's git rules apply: commits only with his yes, on a feature branch, never on `main`; he merges.

## Approaches considered (auth)

1. **Workload Identity Federation, keyless (chosen).** Google Cloud trusts GitHub's OIDC tokens for this repo only; each run gets a short-lived token. Trade-off: one-time setup of a pool, a provider, a service account, and role grants.
2. **Service account JSON key in a GitHub secret.** Five-minute setup. Rejected: the key never expires on its own, and anyone holding it can deploy and rewrite rules. Google recommends against it.

## How it works

### Configuration on GitHub (Kyle adds these as repository variables)

| Variable | Value |
|---|---|
| `FIREBASE_PROJECT_ID` | `whiteicecreambets` |
| `FIREBASE_API_KEY` | web app `apiKey` |
| `FIREBASE_APP_ID` | web app `appId` |
| `FIREBASE_AUTH_DOMAIN` | `whiteicecreambets.web.app` |
| `ADMIN_EMAIL` | the admin's Google email |
| `WIF_PROVIDER` | full resource name of the workload identity provider |
| `WIF_SERVICE_ACCOUNT` | email of the deploy service account |

These are variables, not secrets: the Firebase web config is public by design, and the admin email already ships in the site's JavaScript. Nothing secret is stored in GitHub. (Claude's call.)

### Build-time settings

- The build reads `VITE_*` values from environment variables in CI (Vite already does this), mapped from the repository variables, with `VITE_USE_EMULATOR=false`.
- `scripts/build-rules.mjs` must accept the admin email from the `VITE_ADMIN_EMAIL` environment variable, falling back to `.env.local` as today. It keeps lowercasing and validation, and still fails loudly if neither is set.
- The deploy uses `--project` from `FIREBASE_PROJECT_ID`, never `.firebaserc` (which stays on `demo-wicb` for emulator tests).
- The deploy job checks the built bundle doesn't contain `demo-wicb` or the test admin email before deploying. (Claude's call, cheap guard for the anti-goal.)

### One-time Google Cloud setup (Kyle, in Cloud Shell)

A short script in the repo docs, with the project and repo filled in:
1. Enable the IAM, IAM Credentials, Security Token Service, and Firebase-related APIs the deploy needs.
2. Create a service account `github-deploy` with only the roles the deploy needs (Firebase Hosting admin, Firebase Rules admin, Firestore index admin, and Service Usage consumer, or the builder's verified minimum).
3. Create a workload identity pool and a GitHub OIDC provider whose attribute condition limits trust to `repository == 'lintemurion/white-ice-cream-bets'`.
4. Allow principals from that repository to impersonate the service account (`roles/iam.workloadIdentityUser`).
5. Print the two values Kyle pastes into GitHub (`WIF_PROVIDER`, `WIF_SERVICE_ACCOUNT`).

### Workflows

- **On pull request:** install, `npm test` (Java 21 set up), `npm run build`. No credentials requested.
- **On push to `main` and on manual run:** the same test and build job, then a deploy job that only starts if tests pass. The deploy job authenticates with `google-github-actions/auth` (WIF), regenerates rules, and runs `firebase deploy --project <FIREBASE_PROJECT_ID>`.
- Only one deploy runs at a time; a newer deploy waits for the running one to finish instead of cancelling it mid-upload. (Claude's call.)
- Workflow permissions are least privilege: `contents: read` everywhere; `id-token: write` only on the deploy job.
- Third-party actions pinned to a major version at minimum. (Builder may pin to commit SHAs.)

## How we'll know it works

1. A PR shows the test-and-build check passing.
2. After merging PR #1 (or a manual run), the deploy job authenticates without any key, deploys, and `https://whiteicecreambets.web.app` serves the app.
3. Kyle signs in as admin and sees the admin page (proves the rules have the right admin email).
